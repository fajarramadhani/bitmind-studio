# CMS Security

## Authorization

`public.profiles` contains administrator identities linked to `auth.users`. This phase supports the `admin` role only. Profiles cannot be created or promoted from browser-controlled sign-up metadata; bootstrap the first administrator through trusted SQL.

The role has no database default. Trusted bootstrap SQL must set `role = 'admin'`
explicitly so imports or future profile creation cannot grant administration by
omission.

`public.is_admin()` is a `SECURITY DEFINER` function with an empty controlled `search_path` and fully qualified references. Execute permission is limited to authenticated users. The service-role key bypasses RLS and must remain server-only.

## Row-level security

RLS is enabled on `profiles`, `projects`, `project_media`, `products`, and `product_media`.

- Anonymous and ordinary authenticated users can read only published projects and products.
- Media metadata is readable only when its parent has `publish_status = 'published'`.
- A separate admin policy allows administrators to read drafts and archived rows and perform CRUD.
- Profiles have no public or self-service policy.
- Published rows require `published_at`; availability and publication are independent product states.

The audit trigger fills `created_by` and `updated_by` from `auth.uid()` when a request has an authenticated actor. Trusted SQL can seed content without an actor, leaving those nullable foreign keys unset.

## Private media

Both Storage buckets are private. There is no public or ordinary authenticated object-read policy. Admins can read and perform CRUD, while the public website uses short-lived signed URLs generated by trusted server code.

This guarantee assumes the migration is applied to a clean project. Before adapting
it to an existing Supabase project, inspect and remove any unrelated permissive RLS
policies on the CMS tables or `storage.objects`.

Object names must use an entity UUID directory and collision-safe UUID filename. Bucket MIME and size restrictions permit PNG, JPEG, WebP, and AVIF up to 8 MiB. MIME validation is not malware scanning.

Never persist signed URLs because they expire. Keep `storage_path` as the durable reference and generate a signed URL when serving the page. Never expose `SUPABASE_SERVICE_ROLE_KEY` in a browser bundle or `NEXT_PUBLIC_` environment variable.

Database deletion does not automatically remove a Storage object. Application workflows must clean up both resources. Future private-file categories, audit history, malware scanning, approval workflows, and rate limiting require separate controls.
